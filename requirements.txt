# Securityzator zero-to-secured-tenant requirements
# Last updated: 2026-04-13
#
# Goal:
# A brand-new tenant should be able to move from initial onboarding to
# "Securityzator can collect recommendations and apply the supported controls"
# without hidden prerequisites.

5. App registration model
- Use a dedicated Entra app registration for each customer tenant, or a managed multitenant SaaS pattern when the product is ready for it.
- Today's app model assumes:
  - tenant ID
  - client ID
  - client secret for Graph and CA automation
  - automation certificate for Exchange-backed automation
- The app registration must receive admin consent after permission changes.
- Stage-0 target for a brand-new tenant:
  - Securityzator should be able to start from an Azure CLI delegated Global Administrator session, create the dedicated app registration, create the service principal, stamp the redirect URI / callback URL, generate the initial client secret, bind the automation certificate, grant admin consent, assign workload roles, and then persist the ready-to-use connection record back into the product without manual copy/paste steps.
- Current implementation status:
  - tenant-side permission and role stamping exists
  - automation certificate binding exists
  - connection persistence exists
  - connection records now carry an operator-declared tenant license and capability profile so playbooks can distinguish license gaps from pure provider gaps
  - full app-registration creation and secret generation from zero is still a required bootstrap milestone and should become the default onboarding path
- Hosted-product auth direction:
  - for production onboarding, Securityzator should use browser-based Microsoft Entra interactive sign-in plus admin-consent flows for the tenant administrator
  - do not design the hosted app around collecting or storing Global Administrator usernames and passwords
  - popup or redirect sign-in is the right future operator experience; device-code stays acceptable only as a bootstrap fallback for headless or terminal-first admin setups
- Hosted-product operating model:
  - `Bootstrap plane`
    - tenant admin signs in interactively from the client-facing product UI
    - Securityzator requests tenant admin consent and aligns the tenant app footprint
    - use delegated admin sign-in only for initialization or explicit exception flows
  - `App-only execution plane`
    - the web app and worker should execute recurring collection and remediation through the app identity wherever the provider supports application permissions
    - post-bootstrap, normal execution should not depend on a standing delegated Global Administrator user context
  - `Delegated exception plane`
    - keep just-in-time delegated admin prompts only for the provider surfaces that still do not support safe app-only automation
    - do not model this as permanent user impersonation
- Hosted-product storage direction:
  - local JSON state and local key rings are acceptable for development and controlled self-hosted rollout
  - client-facing enterprise hosting should move operators, tenant connections, jobs, runs, workers, and recommendation state into a database-backed tenant or workspace model
  - client secrets and certificate material should move behind a vault-backed boundary before client-facing launch

9. Tenant-side Entra admin role assignments for the Securityzator service principal
- `Exchange Administrator`
  Required for Exchange Online / Defender for Office automation.
- `Teams Administrator`
  Required for Teams meeting policy automation.
- More roles may be added later for SharePoint / Purview / other workloads, but these two are the current workload-specific app-role requirements.

10. Human operator roles required during bootstrap
- For first-time tenant preparation, use a privileged delegated admin account that can:
  - grant admin consent to app permissions
  - assign Entra roles to the Securityzator service principal
  - validate workload admin access
- In practice, `Global Administrator` works for the bootstrap.
- After setup, day-to-day operations should use least privilege wherever possible.
- Hosted best-practice note:
  the client-facing product should treat this role as a bootstrap or exception-only identity, not as the long-term execution identity of the service.

11. Minimum tenant licensing for the current Business Premium control set
- `Microsoft 365 Business Premium`
  This gives the baseline Securityzator target surface currently mapped and prioritized:
  - Microsoft Entra ID P1
  - Microsoft Defender for Office 365 Plan 1
  - Microsoft Defender for Business
  - Intune Plan 1
- Business Premium is sufficient for:
  - Secure Score sync
  - the current Conditional Access quick wins
  - Safe Links / Safe Attachments baseline work
  - a meaningful subset of Microsoft security recommendations
- Important operational note:
  Business Premium can include Intune Plan 1 on paper, but endpoint-oriented recommendations can still come back thin or non-actionable if Intune entitlement is not effectively assigned, the tenant MDM authority is not active, or devices are not enrolled yet.

12. Additional licensing required for broader April 2026 best-practice coverage
- `Enterprise Mobility + Security E5`
  This is the most relevant next-step uplift from the current Business Premium baseline.
  It materially opens these Securityzator control paths:
  - `Microsoft Entra ID P2`
    Unlocks full Identity Protection and other P2 features such as:
    - sign-in risk policies
    - user risk policies
    - Privileged Identity Management design paths for later admin-hygiene controls
  - `Microsoft Defender for Cloud Apps`
    Unlocks the broader Cloud Apps onboarding, discovery, app governance, and connected-SaaS control families.
  - `Microsoft Defender for Identity`
    Unlocks the licensing side of Defender for Identity onboarding and the AD / AD CS / Entra Connect hardening families.
  - `Azure Information Protection Premium P2`
    Unlocks the advanced information protection path used by auto-labeling and recommended classification controls.
- `Microsoft Entra ID P2` or `Microsoft Entra Suite`
  Required if the tenant does not take EMS E5 but still wants full Microsoft Entra ID Protection risk-policy automation.
- `Microsoft Defender for Identity` standalone or equivalent suite inclusion
  Required for Defender for Identity onboarding and sensor-based identity controls when EMS E5 is not the chosen route.
- `Microsoft Defender for Cloud Apps` standalone or equivalent suite inclusion
  Required when EMS E5 is not the chosen route and the tenant still wants full Cloud Apps discovery, governance, and SaaS protection.
- `Microsoft 365 E5 / A5 / G5` or `Microsoft Defender Suite`
  Required for Safe Documents.
  Safe Documents is not included in Defender for Office 365 Plan 1 or Plan 2 alone, and EMS E5 does not add it.
- Additional Purview / compliance licensing may be required before future data-protection playbooks can be fully automated.
- Important scope note:
  EMS E5 does not, by itself, add the missing workload administration surfaces for Exchange, SharePoint, or Teams, and it does not upgrade Intune beyond Plan 1. Business Premium already includes Intune Plan 1, so EMS E5 helps most on identity, Cloud Apps, Defender for Identity, and advanced information protection rather than core device management.
- Practical alternate working bundle:
  - `Microsoft 365 Business Basic` + `Microsoft Entra ID P2` + `Intune Plan 1` + `Microsoft 365 E5 Security` is a valid Securityzator target profile for the current identity, endpoint, Defender for Cloud Apps, and Defender for Identity paths.
  - With that bundle, Securityzator should treat endpoint capability as satisfied by `Defender for Endpoint Plan 2`; a separate legacy `ATP` add-on is not required for the current Defender work.
  - Important nuance:
    if a tenant mixes `Defender for Business` and `Defender for Endpoint Plan 2` across the same population, Microsoft can keep the tenant in the Defender for Business experience until licensing is cleaned up, so keep the endpoint entitlement model consistent where possible.

13. Fresh-tenant prerequisites before Securityzator can fully harden it
- The tenant must be provisioned and reachable.
- Exchange Online must be active if mail protection baselines are expected.
- Teams must be active if Teams policy baselines are expected.
- At least one emergency / break-glass admin account should exist and be excluded from broad user-targeted CA policies.
- Administrator groups for scoped rollouts should exist if policies will target specific populations instead of tenant-wide assignment.
- Users must have usable MFA-capable methods registered before broad MFA enforcement is switched from report-only to production enforcement.
- Devices must be onboarded to Intune / Defender for Business for endpoint-oriented recommendations to become truly actionable.
- The tenant must have effective Intune entitlement on the target users or devices, and MDM authority must be active, before endpoint and device-compliance signals can be trusted as complete.
- Hybrid identity servers must exist and be onboarded before Defender for Identity recommendations can be completed.
- Pre-AD / hybrid runway reference:
  - `docs/runbooks/pre-ad-checklist.md`

- Recommended fresh-host staged fallback order:
  - 1. Sign in once with Azure CLI for the tenant bootstrap account:
    - `az login --tenant <tenant-id> --allow-no-subscriptions --use-device-code`
  - 2. If the tenant does not already have a dedicated Securityzator app registration, the bootstrap target state is:
    - create the app registration
    - create the service principal
    - stamp the callback / redirect URL
    - generate the initial client secret
    - persist the resulting connection details into Securityzator
  - 3. Install modules and bind the saved Exchange automation certificate:
    - `powershell -ExecutionPolicy Bypass -File .\bootstrap.ps1 -InstallModules -BindExchangeCertificate -UseAuthTxt -ConnectionId <connection-id> -IncludeExchange $true -IncludeTeams $false`
  - 4. Stamp the tenant-side Exchange prerequisites through the targeted helper:
    - `powershell -ExecutionPolicy Bypass -File .\tools\Grant-ExchangeTenantRequirements.ps1 -UseAuthTxt -UseAzureCliDeviceCode -Assign`
  - 4a. Stamp the current tenant-side Microsoft Graph prerequisites through the targeted helper when the app needs Entra daily-use or Intune write alignment:
    - `powershell -ExecutionPolicy Bypass -File .\tools\Grant-GraphTenantRequirements.ps1 -UseAuthTxt -UseAzureCliDeviceCode -Assign -PermissionProfile Current`

    - `Office 365 Exchange Online / Exchange.ManageAsApp`
    - `Exchange Administrator`

    - `powershell -ExecutionPolicy Bypass -File .\tools\Apply-ExchangeAntiPhishBaseline.ps1 -UseAuthTxt -UseAzureCliDeviceCode`
    - if the anti-phish helper needs the fuller Exchange cmdlet surface, rerun it from PowerShell 7 with device login:

    - `powershell -ExecutionPolicy Bypass -File .\tools\Apply-ExchangeSpamAndForwardingBaseline.ps1 -UseAuthTxt -UseAzureCliDeviceCode`
    - `powershell -ExecutionPolicy Bypass -File .\tools\Apply-ExchangeSafeLinksAndAttachmentsBaseline.ps1 -UseAuthTxt -UseAzureCliDeviceCode`
  - 7. Re-run the targeted smoke for the Defender baseline you want to activate.
  - 8. Run the Teams-only bootstrap later when you are ready to enable Teams automation:
    - `powershell -ExecutionPolicy Bypass -File .\bootstrap.ps1 -InstallModules -UseAuthTxt -ConnectionId <connection-id> -GrantTenantRequirements -AssignDirectoryRoles -UseAzureCliDeviceCode -IncludeExchange $false -IncludeTeams $true`
- Bootstrap behavior notes for a brand-new rig:
  - The script is designed to reuse an existing Azure CLI session when the tenant matches, so the normal zero-to-ready path should not keep prompting for repeated sign-in.
  - The bootstrap writes a short-lived local auth cache file `.bootstrap-auth.json` in the repo during delegated tenant setup and clears it on exit.
  - If PowerShell script execution is blocked, use a process-scoped bypass for the current shell rather than changing machine policy:
    - `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`
- The bootstrap script is intended to:
  - install missing host modules
  - bind the Exchange automation certificate to the Entra app and saved connection
  - reuse or request delegated admin login
  - grant required app permissions
  - assign `Exchange Administrator` and `Teams Administrator` to the service principal

19. Known roadmap gaps that are not just permission problems
- SharePoint, Purview, and some Defender workload providers are not fully automated in the product yet.
- Some recommendation families are mapped and staged but still guided or semi-manual rather than fully executable.
- Tenant hardening that depends on server deployment, endpoint onboarding, or premium licensing cannot be solved by Graph permissions alone.
- Client-facing hosting gaps still open:
  - local file-backed state instead of database-backed tenant/workspace storage
  - local operator-account bootstrap instead of enterprise identity-backed operator login
  - shared filesystem Data Protection and worker-state assumptions instead of cloud-friendly shared backing services
  - local host certificate-store assumptions for some workload providers
  - Azure CLI and `Auth.txt` assumptions still present in the local fallback path
  - some workload providers still require delegated exception handling rather than clean app-only execution

20. Practical definition of "ready to securityize a fresh tenant"
- Ready for today's supported scope means:
  - host requirements are met
  - bootstrap script can run
  - app permissions are consented
  - Exchange and Teams app roles are assigned where needed
  - automation certificate is bound
  - Business Premium workloads are provisioned
  - break-glass exclusions are prepared
- Ready for broader best-practice coverage means all of the above plus:
  - premium licensing for risk-based identity and Safe Documents scenarios
  - Defender for Identity rollout
  - endpoint onboarding
  - future workload providers as Securityzator adds them
- Ready for client-facing enterprise hosting means all of the above plus:
  - browser-based tenant onboarding inside the product
  - database-backed tenant/workspace storage
  - vault-backed secret and certificate handling
  - enterprise identity-backed operator login
  - stateless web tier with worker-host separation
  - app-only execution as the default path and delegated admin prompts only for explicit exceptions

21. Permanent Microsoft Graph source map
- `graph.source-map.psd1` is the machine-readable map of the Microsoft-owned sources that Securityzator should trust when permissions, endpoint behavior, or schema stability matter.
- Canonical source split:
  - `microsoft-graph-docs-contrib` for endpoint permissions and documented request/response behavior
  - `msgraph-metadata` for schema permanence and path validation
  - `msgraph-sdk-powershell` for examples and operator ergonomics, not bootstrap truth when SDK behavior diverges
- `bootstrap.requirements.psd1` should remain the curated bootstrap subset derived from `graph.source-map.psd1`.
- `control-catalog.map.psd1` should remain the machine-readable contract for the surfaced Business Premium recommendation cards and the extended template families that keep control routing durable.
- `docs/microsoft-graph-source-map.md` explains the update workflow so new control mappings stay tied to Microsoft-owned guidance instead of one-off notes.

## Host trust and Defender posture
- Use `pwsh` as the default operator shell for Securityzator automation.
- Prefer compiled .NET helpers for validation, export, smoke, and bootstrap logic so the host sees normal signed binaries instead of large ad hoc scripts.
- Keep PowerShell wrappers thin and focused on Microsoft admin modules that require PowerShell, such as Exchange Online or Teams.
- Treat Authenticode signing as the rollout target for `.ps1`, `.psm1`, and `.psd1` files.
- Prefer publisher or managed-path allow rules in App Control / AppLocker over broad antivirus exclusions.
- Keep `ExecutionPolicy Bypass` limited to explicit local bootstrap or troubleshooting, not the long-term operator path.
- See `docs/host-trust-and-defender.md` for the fuller operating model.

## Microsoft Graph API version posture
- Keep `v1.0` as the primary Microsoft Graph surface for stable platform calls.
- Keep `beta` configured as a fallback surface for platform calls that already work in Securityzator when Microsoft moves endpoint shape or property coverage ahead of `v1.0`.
- Do not build brand-new production-only features on undocumented beta-only behavior without recording the dependency and a fallback plan.
