[1] Exchange PowerShell scripts — -CommandName removal
Files: src/Securityzator.Infrastructure/Exchange/DefenderForOfficeAutomationClient.cs
       tools/Apply-ExchangeAntiPhishBaseline.ps1
       tools/Apply-ExchangeSpamAndForwardingBaseline.ps1
============================================================================================

ROOT CAUSE BEING FIXED:
  Exchange Online's REST proxy (Connect-ExchangeOnline) has a lazy-load behaviour
  when -CommandName is used: it only loads the listed cmdlets and returns trimmed
  parameter metadata for each. In app-only certificate mode this strips parameters
  that are not in the slim REST manifest — specifically MailboxIntelligenceProtection-
  Action, EnableTargetedDomainsProtection, TargetedDomains*, and Set-AtpPolicyForO365
  entirely. The spam/forwarding session had NO -CommandName and worked correctly.
  The other four sessions had -CommandName and were silently skipping parameters.

CHANGES:
  DefenderForOfficeAutomationClient.cs:
    - Removed -CommandName from the Connect-ExchangeOnline call in four inline
      PowerShell script strings: anti-phish, Safe Links/Attachments,
      collaboration/mailbox, and anti-malware. The spam/forwarding script was already
      correct and left untouched.
    - Added ApplyAntiMalwareBaselineAsync public method (and its private script
      builder BuildApplyAntiMalwareBaselineScript) so the anti-malware baseline is
      now a first-class executable template rather than a stub.
    - Added MalwareFilterPolicyName / MalwareFilterRuleName constants.

  Apply-ExchangeAntiPhishBaseline.ps1 (standalone tool script):
    - Added Get-CommandParameterNames helper: reflects the actual parameter list of
      a named cmdlet at runtime via Get-Command, so the script can self-describe its
      capability surface without relying on the trimmed manifest.
    - Added Test-ParameterSupported helper: thin boolean wrapper around the above.
    - Added Get-AntiPhishCapabilities / Get-MissingAntiPhishCapabilityDescriptions:
      build a capability map (SupportsMailboxIntelligenceProtectionAction, etc.) at
      runtime. If a parameter is missing the script notes the gap instead of crashing.
      This is defensive: even after removing -CommandName, the capability check
      ensures the script handles future API surface changes gracefully.

  Apply-ExchangeSpamAndForwardingBaseline.ps1 (standalone tool script):
    - Split the Set-HostedContentFilterRule and Set-HostedOutboundSpamFilterRule
      calls to no longer pass -Enabled $true inline. In some Exchange Online
      environments passing -Enabled on Set-* raises an error because the -Enabled
      parameter was moved to Enable-HostedContentFilterRule / Enable-Hosted
      OutboundSpamFilterRule. Now calls Set-* first, then Enable-* separately with
      -Confirm:$false. This matches the pattern already used by the anti-phish script.

SIDE EFFECTS:
  - Full Exchange module load is ~3-5s slower per connection (no -CommandName means
    no lazy loading). Acceptable given the gain in full parameter surface.
  - ApplyAntiMalwareBaselineAsync is now callable from ConditionalAccessRemediationService
    via the ExecuteDefenderForOfficeAntiMalwareBaselineAsync private method.

[2] Application layer — AllUsersAssignment propagated through the request/record chain
Files: src/Securityzator.Application/Remediations/QueueableRemediationTemplateRequest.cs
       src/Securityzator.Application/Jobs/EnqueueQueueableTemplateJobRequest.cs

       src/Securityzator.Application/Jobs/RemediationJobWorkItem.cs
       src/Securityzator.Application/Portal/RemediationTemplateTargeting.cs
============================================================================================

WHY:
  Intune policy assignment currently requires a pilot Entra group object ID. Any
  operator without a pre-created group cannot run an Intune baseline. Microsoft Graph
  supports allDevicesAssignmentTarget for device-configuration policies (all managed
  devices, no group required). The fix threads a boolean flag through every layer of
  the pipeline: web form → job queue → state file → worker → execution engine.

WHAT CHANGED:
  QueueableRemediationTemplateRequest and EnqueueQueueableTemplateJobRequest:
    - Added `bool AllUsersAssignment = false` as the last optional parameter.
    - Default = false: all existing call sites that don't supply it keep the existing
      pilot-group behaviour unchanged.

  RemediationJobRecord and RemediationJobWorkItem (positional records):
    - Added `bool AllUsersAssignment` between ExcludeGroupId and the next member
      (PolicyId / AttemptCount). All constructors in FileBackedRemediationJobService
      were updated accordingly (see [3] below).

  RemediationTemplateTargeting:
    - Added `bool SupportsAllUsersAssignment = false` as the fifth optional parameter.
    - Default = false: all existing CA and Exchange templates unaffected.
    - The view model and Razor view read this to decide whether to show the
      "all devices" toggle in the UI.

[4] Blueprint catalog — new templates and SupportsAllUsersAssignment
File: src/Securityzator.Infrastructure/Blueprints/BusinessPremiumBlueprintCatalog.cs
============================================================================================

WHY:
  (a) Two templates were missing: entra-low-impact-app-consent and
      mdo-anti-malware-baseline. Without catalog entries they cannot be selected
      from the UI or dispatched by the service.
  (b) All Intune pilot templates need SupportsAllUsersAssignment = true so the
      "all devices" toggle appears in the frontend for those templates.

WHAT CHANGED:
  New template: "entra-low-impact-app-consent"
    - Sets the tenant's default user consent policy to allow low-impact delegated
      permissions from verified publishers or tenant-registered apps, while keeping
      risky-app consent disabled and preserving owned-resource consent policies.
    - Targeting: tenant-wide, no pilot group (SupportsIncludeGroupSelection = false,
      SupportsExcludeGroupSelection = false).
    - DefaultLaunchMode = DirectApply. This is an explicit tradeoff template — it
      deliberately does NOT max Secure Score (which requires fully disabling user
      consent) but is the practical safe default for tenants that need users to be
      able to consent to verified low-risk integrations without admin approval on
      every request. The template notes explain this so operators understand.

  New template registration: "mdo-anti-malware-baseline"
    - Registers the anti-malware template in the catalog so it appears in the UI
      and can be selected for remediation.

  SupportsAllUsersAssignment = true added to 10 Intune targeting blocks:
    - core-protection, firewall-and-smartscreen, exploit-protection, bitlocker,
      credential-and-elevation-hardening, remote-access-and-network-hardening,
      browser-hardening, attack-surface-reduction, os-security-baseline,
      sensor-and-agent-health-assessment.
    - CA templates (block-legacy-auth, require-mfa-admins,
      require-phishing-resistant-mfa-admins) were NOT changed — they use the Entra
      "Users and groups" CA assignment model, not Intune device assignment targets.

  Safe Links/Attachments template description change:
    - Removed "Create zero-hour auto purge policies for malware" and
      "Ensure the Common Attachment Types Filter is enabled" from the Safe Links
      template description because those controls belong to the anti-malware template,
      not to Safe Links. This was a categorisation error in the original catalog.

[6] Intune client — allDevicesAssignmentTarget support
File: src/Securityzator.Infrastructure/Intune/IntuneEndpointAutomationClient.cs
============================================================================================

WHY:
  Microsoft Graph Intune assignment API accepts three target types. The client only
  ever emitted groupAssignmentTarget. When AllUsersAssignment is true, it must emit
  allDevicesAssignmentTarget instead.

KEY TYPES:
  #microsoft.graph.groupAssignmentTarget      — specific Entra group (pilot)
  #microsoft.graph.allDevicesAssignmentTarget — all enrolled Windows devices
  #microsoft.graph.exclusionGroupAssignmentTarget — still emitted when excludeGroupId
                                                    is set, even in all-devices mode

WHAT CHANGED:
  EndpointAssignmentTargetSnapshot nested DTO:
    - Added `public bool IsAllDevicesTarget` computed property. Checks the odata type
      string for both '#microsoft.graph.allDevicesAssignmentTarget' and the variant
      without the leading '#', since Graph read responses can return either form.

  ValidatePilotAssignment (private):
    - Parameter order changed: allUsersAssignment now comes BEFORE baselineName.
      This matches the call-site pattern used by all 9 public Apply* methods.
    - When allUsersAssignment = true: skips the Guid.TryParse check on includeGroupId
      (an empty group ID is valid in all-devices mode).
    - When allUsersAssignment = true: skips the include==exclude collision check.

  AreAssignmentsAligned (private):
    - Added `bool allUsersAssignment = false` as the fourth parameter.
    - When true: checks that exactly one assignment has IsAllDevicesTarget = true and
      no unexpected group-type assignments exist. Exclusion-group assignments are
      still permitted.
    - When false: original group-ID comparison logic is unchanged.

  AssignConfigurationAsync (private, deviceConfigurations endpoint):
    - Added `bool allUsersAssignment = false` after CancellationToken.
    - When true: emits { "@odata.type": "#microsoft.graph.allDevicesAssignmentTarget" }.
    - When false: emits { "@odata.type": "...groupAssignmentTarget", "groupId": "..." }.

  AssignGroupPolicyConfigurationAsync (private, groupPolicyConfigurations endpoint):
    - Same change as AssignConfigurationAsync. This endpoint is used by the browser
      hardening baseline which goes through a different Graph API surface.

  All 9 Apply*BaselineAsync public methods + AssessEndpointSensorAndAgentHealthAsync
  + AssessBitLockerDeploymentStateAsync:
    - Added `bool allUsersAssignment = false` before CancellationToken in every
      method signature.
    - Threaded allUsersAssignment to every ValidatePilotAssignment,
      AreAssignmentsAligned, AssignConfigurationAsync, and
      AssignGroupPolicyConfigurationAsync call site within each method.
    - AssessBrowserAndAdobePolicySurfaceAsync takes no group parameters and is
      unchanged.

File: src/Securityzator.Infrastructure/Graph/DirectoryGraphClient.cs

WHY:
  The new entra-low-impact-app-consent template needs a Graph API implementation.
  This is a write-path change to the tenant's authorizationPolicy. It also needs
  to update the identity-hygiene assessment to recognise the low-impact consent
  posture as distinct from "still enabled" so operators don't see a false NeedsFollowUp.

WHAT CHANGED:
  New constants:
    - LowImpactUserConsentPolicyAssignment: the built-in policy identifier
      "managePermissionGrantsForSelf.microsoft-user-default-low".
    - OwnedResourcePolicyPrefix: "managePermissionGrantsForOwnedResource." — used to
      identify and preserve any owned-resource policies that were already in place.

  ApplyEntraLowImpactAppConsentAsync (new internal method):
    - Reads the current authorizationPolicy.
    - Preserves any existing owned-resource consent policy assignments (these are
      distinct governance policies that should not be clobbered).
    - Builds desiredPolicies = preserved owned-resource assignments +
      LowImpactUserConsentPolicyAssignment.
    - If already aligned (correct policies, risky-app consent disabled), marks as
      already compliant. Otherwise PATCH-updates the policy via
      UpdateAuthorizationPolicyAsync.
    - Performs a readback to capture the after-state.
    - Returns EntraLowImpactAppConsentResult with before/after snapshots and notes.

  BuildUserConsentFinding (updated):
    - Added lowImpactConsentEnabled detection using HasLowImpactUserConsentAssignment.
    - Summary now has three branches: disabled (Satisfied) / low-impact-only
      (ManualReview — passes, but reviewer should note it is not max posture) /
      broad consent still enabled (NeedsFollowUp).

  BuildConsentManagementFinding (updated):
    - Added a third posture narrative branch: low-impact consent + admin workflow
      enabled is described as "safer than broad user consent but still leaves room
      for approved low-impact app grants."

  New private helpers:
    - HasLowImpactUserConsentAssignment: boolean check on the policy list.
    - IsOwnedResourcePolicyAssignment: checks for the owned-resource prefix.
    - HaveSamePolicyAssignments: order-insensitive, case-insensitive set equality
      for two policy-assignment lists (used to avoid unnecessary patches).
